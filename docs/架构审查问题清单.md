## 3. P0 问题：对应模块开发前必须解决

### AUD-P0-01：原型新增业务规则尚未回填架构文档

**类型：** 文档一致性问题 / 需求变更未固化  
**状态：** 阻塞 Vocabulary、Task、Dictation、Practice 的最终 Schema  
**证据：**

- 原型已有 `subject: 'english' | 'chinese'`。
- 原型已移除词库分类 UI，但类型和存储仍保留 `category`。
- 原型任务创建由勾选词条决定数量，固定和长期任务都不再填写学习数量。
- 原型支持 `2-10`、`4,8` 等词条范围。
- 原型支持线上/线下听写、自动/手动播放、朗读次数、播放间隔和提示内容。
- 原型允许页面直接创建任务，并允许从已发布公共词库创建任务。
- 原型支持在 Agent 确认卡中编辑全部任务或词库字段。

**影响：**

- 架构文档没有定义学科模型、词条选择输入、听写扩展配置和页面任务创建的正式业务规则。
- 如果后端直接按当前代码实现，会把原型实现细节误当成正式规则。
- 如果完全不按原型实现，正式前端将出现大量返工。

**建议：**

1. 新增一份“V1.0 产品决策补遗/变更记录”，逐项列出原型后确认的产品变化。
2. 明确哪些属于 V1 正式范围，哪些只保留在原型。
3. 在进入 Vocabulary Schema 和 Task Schema 开发前更新架构文档对应章节。

**阻塞判断：** 不阻塞 Phase 0；阻塞 Phase 2 及之后的领域模型定稿。

---

### AUD-P0-02：“词库分类”是否正式移除尚未裁决

**类型：** 业务规则冲突  
**状态：** 阻塞 Vocabulary 数据表最终设计  
**证据：**

- 架构文档第 18 节明确：“分类采用预设分类 + 自定义标签。”
- 前端原型已移除创建、详情和列表中的分类输入/展示。
- `Vocabulary` 和 `VocabularyDraft` 类型仍保留 `category`，创建时写入“未分类”。

**影响：**

- 数据库是否需要 `category` 字段、分类字典表和索引无法确定。
- 如果后端保留分类而前端永远不填，会形成长期无效字段。
- 如果正式移除，需要更新架构文档并说明历史数据如何处理。

**建议：**

在 Vocabulary Schema 设计前从以下方案中选择：

- A. 正式移除分类，只保留学科和自定义标签。
- B. 保留分类为内部可选字段，但 V1 UI 不展示。
- C. 重新开放分类，但要定义预设分类和权限。

**推荐：** 若最新产品方向明确为“只按学科和标签组织”，选择 A，并更新架构文档。

---

### AUD-P0-03：可编辑确认卡与 action_id / 配置 Hash 机制不一致

**类型：** Agent 确认协议 / 幂等风险  
**状态：** 阻塞 Agent 任务与词库确认流程开发  
**证据：**

- 架构文档要求：配置变化后必须生成新的 `action_id`，确认请求还要校验配置 Hash。
- 原型中 `TaskActionEditor` 和 `VocabularyActionEditor` 可以在确认卡中持续修改配置。
- `ActionPreview` 修改本地 draft 后仍沿用原 action 的 `id` 提交。
- 现有执行记录只保存已执行的 action_id，没有服务端配置 Hash。

**影响：**

- 用户可能确认的内容与实际展示内容不一致。
- 重试、并发或页面刷新后无法可靠判断确认的是哪一版配置。
- 直接沿用当前原型逻辑会破坏架构中已确认的幂等和确认安全规则。

**建议：**

正式协议必须增加“草稿更新/重新预览”流程。例如：

1. Agent 返回 `action_id + config_hash + editable_draft`。
2. 前端编辑后调用 `PATCH /agent/actions/{action_id}/draft`。
3. 后端校验并返回新的 `action_id`、新的 `config_hash` 和规范化预览。
4. 用户只能确认最新 action_id。
5. Service 再次校验 action_id、配置 Hash、用户身份和业务状态。

**阻塞判断：** 阻塞 Phase 7 Agent Workflow，不阻塞早期基础设施与业务 Service。

---

### AUD-P0-04：固定/长期任务的数量、词条选择和分组规则需要正式定稿

**类型：** Task / Practice 业务规则  
**状态：** 阻塞 Task 与 Practice 数据模型定稿  
**证据：**

- 架构文档定义固定任务和长期任务，但没有定义“用户勾选子集”这一入口。
- 原型中任务数量自动等于已选词条数量，固定和长期任务都不再单独填写学习数量。
- 长期任务仍可配置每组数量。
- 原型允许通过序号表达式和勾选框选择词条。
- 原型 Agent 修改长期任务时仍可能修改 `targetCount`，与页面规则不完全一致。

**需要确认：**

1. “固定任务”是否只包含用户显式勾选的词条，还是必须覆盖整个词库？
2. 长期任务的目标内容是否是已选词条集合，而非整个词库？
3. 长期任务“所有词汇内容完成”中的“所有”是否指已选集合？
4. 每组数量是否只在长期任务中生效？
5. 修改分组规则是否仍遵守“从下一组开始生效”？
6. 页面和 Agent 是否使用同一套可修改字段集合？

**建议：**

- 后端接收解析后的 `selected_entry_ids`，不接收序号表达式；表达式只在客户端转换。
- Task Service 重新读取词库并验证词条归属，再生成快照。
- 固定任务和长期任务使用同一快照机制，差异只在进度与分组规则。

### AUD-P0-05：线下听写的判分、掌握和任务进度语义未定义

**类型：** Dictation / Practice / Learning 业务规则  
**状态：** 阻塞线下听写和 Learning 规则实现  
**证据：**

- 原型线下听写由用户勾选“我写错了哪些”，未勾选项直接视为正确。
- 该结果与线上自动判分写入同一类 `AnswerRecord`。
- 架构文档没有定义用户自报结果的评分权威性。

**需要确认：**

1. 线下自查结果是否计入正式正确率？
2. 是否标记 `evaluation_source = self_report`，并在 UI/统计中区分？
3. 用户自报正确是否可用于“已掌握”状态？
4. 自报错误是否进入错题和复习计划？
5. 是否允许之后由教师/家长修正？若允许，属于哪个角色和模块？

**建议：**

- 在 Practice Answer 中显式保存判定来源：自动判分 / 用户自查。
- Learning 统计必须知道来源，不能把两种事实完全等同。
- 掌握算法是否采用自查事实，需单独确认。

---

### AUD-P0-06：LangGraph MySQL Checkpointer 尚无可用性结论

**类型：** Agent 持久化技术风险  
**状态：** 阻塞 Agent Runtime 生产化  
**证据：**

- 架构文档明确要求先验证 MySQL 持久化方案，不能自行伪造兼容层。
- 当前前端仅使用 LocalStorage 模拟，不涉及真实 Checkpointer。

**需要验证：**

- LangGraph 当前版本的 Checkpointer 接口和版本约束。
- 是否存在可维护的 MySQL Saver。
- Checkpoint 序列化、事务、并发和迁移方式。
- Interrupt/Resume 的 thread_id 与业务 Conversation 的映射。
- Checkpoint 清理和保留策略。

**建议 PoC：**

- 使用真实 LangGraph 版本完成一次 interrupt → resume → 重复 resume。
- 验证服务进程重启后能否恢复。
- 输出 ADR，明确 MySQL 方案或替代方案。
- 在 PoC 完成前，不实现生产 Agent Graph 持久化。

---

### AUD-P0-07：SSE 断线、事件补发和服务重启恢复方案未确定

**类型：** 通信协议 / 运行状态风险  
**状态：** 阻塞 Agent SSE 正式接入  
**证据：**

- 架构文档明确区分同步执行、SSE 断线后继续运行、服务重启恢复。
- 前端 `AgentEvent` 只有 `type + data`，没有 `event_id`、`run_id`、`conversation_id`、`timestamp`、游标。
- Mock Agent 使用定时器模拟事件，不验证网络断开或重放。

**需要确认：**

1. 是否使用 `POST + text/event-stream` 的同步流，还是先创建执行再 GET SSE？
2. 服务端是否保存可重放事件。
3. 断线后客户端通过什么游标恢复。
4. 如果没有事件补发，前端如何查询最终状态。
5. 同一 Conversation 的锁和异常释放方式。
6. FastAPI 同步 StreamingResponse 在客户端断开后是否继续执行。

**建议 PoC：** 在 Agent Runtime 阶段开始前完成，不以 Mock 延迟代替。

## 4. P1 问题：联调前应解决

### AUD-P1-01：SSE 事件 envelope 与前端类型不一致

**证据：** 原型 `AgentEvent` 只包含 `type/data`。  
**建议：** 正式事件统一为：

```json
{
  "event_id": "evt-...",
  "conversation_id": "conv-...",
  "run_id": "run-...",
  "sequence": 12,
  "type": "progress",
  "timestamp": "2026-11-02T10:00:00+08:00",
  "data": {}
}
```

前端应兼容事件回放和乱序防护。

---

### AUD-P1-02：Prompt 可扩展性需要具体落地方式

**类型：** Prompt 版本管理  
**证据：** 架构要求 Prompt 文件 + Git，未来可能需要管理员查看、编辑、发布和回滚。  
**风险：** 若代码到处直接读取字符串或把 Prompt 拼在 Graph Node 中，未来迁移成本高。  
**建议：**

- 建立 `PromptRegistry` / `PromptTemplate` 抽象，即使实现是文件读取。
- 每次执行记录：
  - prompt_id
  - prompt_version
  - git_commit
  - model/provider
  - template_variables_hash
- Prompt 内容不存敏感配置。
- 当前不建管理后台，但接口边界允许未来替换为数据库版本源。

---

### AUD-P1-03：文件导入有两套事实来源

**证据：**

- Chat Agent 文件上传仍使用 `importedVocabulary(fileName)` 固定模拟数据。
- 页面词库创建使用 `read-excel-file` 在浏览器真实解析。
- Chat 上传控件接受 `.xls`，实际解析器只支持 `.xlsx/.csv`。

**影响：** 正式后端接入时会出现 Agent 导入和页面导入结果不一致。  
**建议：**

- 统一为 Material 上传 → Content 解析 → Content Preview → Vocabulary 确认保存。
- 页面与 Agent 调用同一 Material/Content Service。
- `.xls` 是否支持必须明确；若不支持，所有 UI 移除 `.xls`。
- 后端解析必须设置文件大小、行数、单元格长度和超时限制。

---

### AUD-P1-04：Conversation 与 Message 在原型的存储粒度不符合正式模型

**证据：** LocalStorage 中 Conversation 内嵌完整 `messages` 数组。  
**正式要求：** Conversation 与 Conversation Message 分表，Tool Call 和 Tool Result 独立消息。  
**建议：** 后端不要复用 LocalStorage 数据形状；前端只依赖 API DTO。

---

### AUD-P1-05：任务进度算法仍是原型简化逻辑

**证据：**

- `taskProgressFromAttempt` 使用正确词数 / targetCount，并取历史最大值。
- 原型没有完整实现长期任务分组、强制重做、重复练习不重复累计等规则。
- 原型 `submitAnswer` 的 `questionId` 使用当前索引，不是稳定题目 ID。

**影响：** 正式 Task/Practice 数据与进度结果可能不一致。  
**建议：**

- Task/Practice Service 明确正式进度公式。
- 进度从 Practice 事实可重算。
- Attempt 保存稳定 Question/Snapshot 引用。
- 练习提交和进度更新必须同一事务。

---

### AUD-P1-06：用户自报线下听写结果需要新的事实字段

**建议：** Practice Answer 至少增加：

- `evaluation_source`: `auto | self_report`
- `self_reported_correct`: boolean nullable
- `answer_text` nullable
- `corrected_by` nullable（若未来支持人工修正）

不要把线下自查伪装成普通自动判分。

---

### AUD-P1-07：管理员能力边界需要 API 级验证

**原型现状：**

- 管理员可查看学习概况、重置密码、管理公共词库。
- `mockApi` 的任务接口都要求任务属于当前用户，管理员不能修改用户任务。
- `adminApi.listUsers` 返回了演示密码字段，这只能存在于 Mock。

**正式要求：**

- 用户密码哈希绝不出现在任何 DTO。
- 管理员查询用户学习数据使用只读接口。
- 管理员不能调用普通用户的 Task/Practice 写接口代替用户操作。
- 公共词库管理走 Vocabulary 管理权限，不另建重复业务 Service。

---

### AUD-P1-08：并发、幂等和事务边界尚未落到 API

**需要明确：**

- 同一 Conversation 的运行锁。
- 同一 action_id 的确认锁。
- 同一 Task 同时开始多个 Attempt 的处理。
- 同一词库存词重复的唯一约束。
- 删除任务与练习记录的同一事务。
- 词库复制与版本引用的同一事务。

## 5. P2 问题：可在迭代中处理

### AUD-P2-01：原型类型仍保留已从 UI 移除的 category

**建议：** 等 AUD-P0-02 裁决后统一删除或正式定义。

### AUD-P2-02：学习统计包含固定日期

**证据：** `buildLearningStats` 使用 `2026-11-02T12:00:00+08:00` 作为周统计基准。  
**建议：** 正式实现使用用户时区或服务端统一时区，并明确“最近 7 天”的边界。

### AUD-P2-03：原型没有自动化测试框架

**现状：** 只有 TypeScript 类型检查、构建和人工浏览器验收。  
**建议：** 后端从 Phase 0 建立 pytest；前端后续加入 Vitest + Playwright。

### AUD-P2-04：原型缺少全局错误边界

**建议：** 正式前端增加路由级错误边界和统一错误展示，但不应依赖前端错误边界兜底后端权限错误。

### AUD-P2-05：原型多处依赖浏览器能力

- Web Speech API
- 浏览器 Excel 解析
- LocalStorage

正式实现需要服务端可替代方案或明确降级策略。

### AUD-P2-06：演示管理员数量不是正式业务需求

当前存在 Admin、Manager 两个演示管理员，仅用于原型体验。正式系统不应自动 seed 固定管理员密码，应通过安全初始化流程创建。

## 6. 已确认且应继续遵守的决策

1. React + TypeScript 前端。
2. FastAPI + LangGraph + MySQL；SQLite 仅限开发。
3. Agent 是核心入口，但不是业务逻辑所有者。
4. 所有业务写入通过 Service。
5. 模块之间不能直接访问 Repository 或数据表。
6. Conversation、Checkpoint、业务数据分离。
7. Single Agent + Internal Subgraphs。
8. LLM 理解，程序校验、鉴权和执行。
9. Tool Registry 权限过滤 + Service 二次校验。
10. 重要写操作必须预览并由用户确认。
11. action_id 幂等，配置变化产生新确认。
12. 删除任务采用两阶段确认。
13. 固定任务内容不可修改。
14. 每次练习创建独立 Attempt。
15. 练习中断只保存进度，任务状态没有 paused。
16. 管理员不能修改用户答题、掌握状态或代替用户操作。
17. MVP 不支持多 Conversation、WebSocket、异步 Job/Worker。
18. Prompt 文件化并记录版本。
19. 执行详情脱敏。
20. 正式开发前验证 MySQL Checkpointer。

## 9. 是否阻塞正式开发

**总判断：**

- **不阻塞：** Phase 0 工程基础、CI、配置、日志、数据库迁移框架、测试框架。
- **阶段内阻塞：**
  - Phase 1 Auth 前：登录会话方案。
  - Phase 2 Vocabulary 前：分类/学科最终口径。
  - Phase 3 Task 前：固定/长期与勾选词条规则。
  - Phase 5 Learning 前：线下听写事实口径、掌握与进度算法。
  - Phase 6 Agent Runtime 前：MySQL Checkpointer、SSE 运行模型。

因此建议先批准本清单和实施计划，再开始 Phase 0；不要直接开始 Agent 业务开发。
