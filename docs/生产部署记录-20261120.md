### 背景

`yidongxun.com` 已停止服务，应用在 2026-11-17 临时挂到 `sunxinshan.site/zijixue` 子路径下（前端 base=`/zijixue/`）。本次把正式域名收敛到 `zijixue.xyz`，站点走根路径，前端 base 回到 `/`。

### 实现

**前端（一处改动）**

- `frontend/.env.production`：`VITE_BASE_PATH=/zijixue/` → `/`。
- 无需改代码：`vite.config.ts` 读 `VITE_BASE_PATH` 作为 `base`；`App.tsx` 的 `routerBasename` 与 `httpClient` 的 `API_BASE_URL` 都由 `import.meta.env.BASE_URL` 推导，base 为 `/` 时自动得到 `/api/v1`。
- **按 HEAD 干净构建**（`git worktree`），刻意不带工作区未提交改动：那批改动里的管理页调用了线上后端尚未存在的 `/admin/checkpoints`，混进去会让管理页直接报错。

**Nginx（新增一个站点配置）**

- 新增 `/etc/nginx/conf.d/zijixue.xyz.conf`（源文件 `/opt/project2/nginx/zijixue.xyz.conf`）：
  - 80：仅放行 `/.well-known/acme-challenge/`，其余 301 到 https；
  - 443 `www`：301 到裸域名；
  - 443 裸域：`/api/` → `127.0.0.1:8002`（`proxy_buffering off`，保 SSE 流式），`/` → `127.0.0.1:8003`。
- `sunxinshan.conf` 的 `location ^~ /zijixue/` 改为 `rewrite ^/zijixue/(.*)$ https://zijixue.xyz/$1 permanent`，`= /zijixue` 直接 301 到新域名。旧 URL 全部保留可达。
- 证书独立一张，不与 `sunxinshan.site` 混签：任一域名下线不用重签另一个。

**产物切换**

- 构建产物先上传到 `/opt/project2/releases/.dist-zijixue-new` 暂存，脚本内校验 `index.html` 引用的是 `/assets/` 才允许切换。
- 切换方式：`mv dist dist.bak-<时间戳>` → `mv 暂存目录 dist`。保持 `.../frontend/dist` 这个路径不变，`serve_spa.py` 启动时已 `resolve()` 了该路径，因此**无需重启服务**。

## 2. 修复 Agent「执行失败，请稍后重试」

**上线时间：** 2026-11-20 14:06:58（Asia/Shanghai，`ActiveEnterTimestamp`）
**代码提交：** `3a03d12 fix: revive the MySQL checkpoint connection before each graph call`
**Release：** `/opt/project2/releases/familylearning-3a03d12`（由 `c28331c` 整目录复制，修正 venv shebang）
**回滚目标：** `/opt/project2/releases/familylearning-c28331c`
**数据库：** 无迁移

### 现象与根因

用户在对话里执行操作时报「执行失败，请稍后重试」。日志：

```text
langgraph/checkpoint/mysql/__init__.py:236 get_tuple → cur.execute(...)
pymysql.err.InterfaceError: (0, '')
```

`PyMySQLSaver.from_conn_string()` 只在进程启动时开**一条** `pymysql.Connection`（`autocommit=True`），全程复用，没有连接池、没有探活、没有回收。MySQL 的 `wait_timeout`（生产 28800 秒）会把空闲连接踢掉，但客户端对象留在进程里不会自愈，下一次 checkpoint 读写直接抛 `InterfaceError(0, '')`，被 `runtime.py:403` 兜成通用文案。

时间线吻合：服务 11-17 15:57 启动后未重启，`agent_runs` 里 11-19 07:50 与 11-20 05:57 两次 failed，最后一次成功是 11-05。

**与域名迁移无关**：失败点在 checkpoint 读写，不经过任何 HTTP 路由；业务库走 SQLAlchemy 且有 `pool_pre_ping=True` + `pool_recycle=1800`，所以其它接口一直正常。

### 实现

`backend/app/modules/agent/runtime.py`：

- 新增 `_revive_checkpoint_connection()`：对 `saver.conn` 调 `ping(reconnect=True)`；SQLite 后端没有 `.conn.ping`，直接跳过，行为不变。
- 新增 `_with_checkpoint_retry()`：调用前先探活；遇到 `pymysql.err.InterfaceError` / `OperationalError` 时重连并重试一次，其余异常原样抛出。
- 三处图调用全部包上：`invoke`（新会话与确认恢复）、`get_state`、`update_state`。重试以 LangGraph 的 checkpoint 为界，与用户手动重试语义一致。
- 顺带还原了一处工作区遗留的调试前缀 `logger.info("xxxxxxagent tool calling enabled=...")`。

新增 `backend/tests/test_agent_checkpoint_reconnect.py`（4 条）：断连重试一次、调用前必探活、无 `.conn` 的 saver 不受影响、非连接异常不重试。

### 一个必须记住的部署细节

`app` 包在 release 里存在两份：源码目录 `backend/app/` 与 venv 内的 `site-packages/app/`（后者是早期安装的**残缺副本**，缺 `executor.py`）。生产实际由 uvicorn 把 cwd 插到 `sys.path` 最前，因此**从源码目录导入**，`site-packages/app` 不参与运行。

判断依据（三条互相印证）：

1. `project2-start.sh` 先 `cd "$RELEASE_DIR/backend"` 再跑 `.venv/bin/uvicorn app.main:app`；uvicorn 的 `--app-dir` 默认 `""`，`os.path.abspath("")` 就是 cwd，被 `sys.path.insert(0, ...)`。
2. `site-packages/app/modules/agent/` 缺 `executor.py`，而 `runtime.py` 依赖它；若真的从副本导入，服务根本起不来，但服务正常。
3. 带 `PYTHONPATH=$PWD` 时 `runtime.__file__` 解析到 `releases/familylearning-3a03d12/backend/app/...`，且 `hasattr(_with_checkpoint_retry)` 为 True。

结论：**发布后端只需覆盖 `backend/app/` 下的源码**，不必重装包；也不必改 `site-packages`。本次一度误改了那份副本，已还原。

**⚠️ 这是个埋着的坑**：任何**不在 `backend/` 目录下**执行的脚本（例如 `python /tmp/xxx.py`、或从 `releases/` 根跑工具），`sys.path[0]` 是脚本所在目录，`app` 会落到 venv 里那份残缺旧副本上，**静默使用旧代码**。本次复查时就踩到了（导入报 `cannot import name '_with_checkpoint_retry'`）。跑离线脚本一律带上 `cd backend && PYTHONPATH=$PWD`。

建议后续清理：把 `site-packages/app` 删掉，或换成指向 `backend/app` 的 `.pth`（一行路径），从根上消除双份代码。未在本次执行 —— 属于发布结构调整，需单独确认。
